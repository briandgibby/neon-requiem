## Goal

Establish the canonical safe-zone policy before adding richer mob aggro, follow, elite spawn, and event systems.

Safe zones should suppress automated hostile NPC behavior by default. Event systems can later override this behavior by flipping room-level flags for the affected event area.

Canonical rule:

```ts
effectiveSafeZone = room.isSafeZone && !room.safeZoneOverrideActive
```

---

## Decisions

1. Phase 4.4A blocks **automated hostile behavior only**.
2. Player-initiated combat, PvP rules, reward accounting, event recruitment, and faction allegiance behavior are out of scope.
3. `safeZoneOverrideActive` is the blunt room-level event override for now.
4. The safe-zone rule belongs in the world domain because it governs zone-specific behavior.
5. Use two enforcement checks:
   - Alarm triggering should be blocked in effective safe zones.
   - Reinforcement spawning should also be blocked in effective safe zones.
6. Blocked automated alarms should be clean no-ops with explicit results, leaving room cleanliness unchanged.

---

## Non-Goals

- No full mob aggro/follow pathfinding.
- No elite mob spawn logic.
- No body-guarding mechanics for jacked-in deckers.
- No event scheduler or `WorldEventService`.
- No participation/reward tracking.
- No friendly/faction-aware NPC combat behavior.
- No PvP permission model changes.

## Proposed Implementation

### 1. Add World-Domain Safe-Zone Policy

Likely files:

- `src/domains/world/world.service.ts`
- `src/domains/world/world.types.ts`
- `tests/world/world.service.test.ts`

Add a pure policy helper for callers that already have a room record:

```ts
export function isEffectiveSafeZone(room: Pick<RoomRecord, 'isSafeZone' | 'safeZoneOverrideActive'>): boolean {
  return room.isSafeZone && !room.safeZoneOverrideActive;
}
```

Add a service lookup for systems that only have a room id:

```ts
async isEffectiveSafeZone(roomId: string): Promise<boolean>
```

This keeps combat and future event systems from duplicating room flag logic.

### 2. Block Automated Alarm Triggering

Likely files:

- `src/domains/combat/combat.service.ts`
- `src/engine/security-patrol.ts`
- `tests/combat/combat.service.test.ts`

Update `CombatService.triggerSecurityAlarm(roomId)` to consult the world-domain policy before creating or mutating a combat session.

Recommended return shape:

```ts
type SecurityAlarmResult =
  | { triggered: true }
  | { triggered: false; reason: 'safe_zone' };
```

When blocked:

- Do not create a combat session.
- Do not set `alarmState = RED`.
- Do not set `backupCalled = true`.
- Do not alter room cleanliness.

`SecurityPatrol` can log that a dirty safe-zone room was skipped, but should not otherwise mutate combat state.

### 3. Block Reinforcement Spawning

Likely files:

- `src/engine/ecs/systems/combat-reinforcement-system.ts`
- `src/server.ts`
- `tests/engine/combat-system.test.ts`

Inject the world-domain safe-zone policy into `CombatReinforcementSystem`.

Before spawning reinforcements for a session with `backupCalled && turnsUntilReinforcements === 0`, check the session room:

- If `effectiveSafeZone` is true, do not spawn reinforcements.
- Clear or defer the pending reinforcement state intentionally. Preferred behavior: clear `turnsUntilReinforcements` to avoid retry spam while the room remains protected.
- Preserve the session otherwise.

This second check protects against stale/preexisting combat sessions and event flags changing while backup is pending.

## Test Plan

### World Policy

- `isEffectiveSafeZone` returns true when `isSafeZone = true` and `safeZoneOverrideActive = false`.
- Returns false when the room is not a safe zone.
- Returns false when override is active.
- `WorldService.isEffectiveSafeZone(roomId)` returns false for missing rooms or throws a deliberate domain error. Choose one behavior and test it.

### Alarm Triggering

- `triggerSecurityAlarm` does not create a combat session for an effective safe zone.
- `triggerSecurityAlarm` still triggers RED alert when override is active.
- `triggerSecurityAlarm` still triggers RED alert in non-safe-zone rooms.
- `SecurityPatrol` skips effective safe zones.

### Reinforcement Spawning

- Reinforcements do not spawn into effective safe zones.
- Reinforcements do spawn when override is active.
- Reinforcements do spawn in non-safe-zone rooms.
- Safe-zone blocked reinforcement does not repeatedly spawn or retry every tick.

### Verification Commands

```bash
npm run build
npm test -- --silent
```

Frontend verification is not required unless shared types or UI-visible behavior changes.

## Deferred Event Behavior

Future hostile safe-zone events may intentionally enable aggressive action in normally protected areas by setting `safeZoneOverrideActive = true` on affected rooms.

Examples:

- Insect spirit invasion in a public district.
- Corporate raid spilling into a civic safe zone.
- Law-enforcement containment event where players are recruited to help.

For those events, alarm-like escalation should not automatically mean hostile law/security NPCs attack players. Event-specific behavior may instead spawn friendly or allied security NPCs that fight alongside recruited players against event enemies.

Deferred mechanics:

- Event lifecycle that flips `safeZoneOverrideActive` on start/end.
- Event-specific faction and allegiance rules.
- Friendly NPC support behavior.
- Player recruitment.
- Participation and reward tracking.
- Event cleanup and restoration guarantees.
