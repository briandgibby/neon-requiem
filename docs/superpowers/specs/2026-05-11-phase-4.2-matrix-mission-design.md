# Phase 4.2 Design: ICE Persistence & Matrix-Node Mission Targets

**Date:** 2026-05-11
**Status:** Approved
**Tracks:** ICE/Alert DB Persistence · Matrix-Node Mission Objectives · OS Stub

---

## Context

Phase 4.0 established ECS lifecycle and garbage collection. Phase 4.2 closes two open loops:

1. Matrix ICE HP and node alert levels mutate in ECS but are never written back to the database. A server restart silently resets all Matrix state.
2. Mission objectives of type `HACK_NODE`/`BREACH_NODE` have no ECS entity to attach to, so `MissionSystem` never detects their completion.

This spec also lays a forward-compatible stub for the Overwatch Score (OS) system, which will be fully designed and implemented in Phase 4.3.

---

## Track 1: ICE/Alert Persistence — Immediate Flush

### Principle

Every Matrix action that mutates ECS state calls the matching `MatrixRepository` method before returning. No dirty tracking, no batching. Simple and correct at this scale; optimize if load data justifies it.

### Changes

#### `MatrixService.dataSpike()`

After `moveDispatcher.dispatch('data-spike', ...)` succeeds:

1. Read the ICE entity's `HealthComponent` from the registry.
2. Call `matrixRepo.updateIceHp(ice.iceId, health.current)`.
3. Increment `overwatchScore` on the decker's `DeckerComponent` by 1 (OS stub — see Track 3).

#### `MatrixService.performHacking()` (brute / sleaze)

After dispatch returns (regardless of success):

1. Read the node entity's `MatrixNodeComponent`.
2. Call `matrixRepo.updateNodeAlert(node.nodeId, node.alertLevel)` — alert can escalate even on a failed action, so always flush.
3. If `result.success`, increment `node.breachProgress` by 1.
4. Increment `overwatchScore` on the decker by 1.

#### `MatrixTickSystem` — alert decay flush

The tick system currently mutates `node.alertLevel` in memory. It now receives `MatrixRepository` via constructor injection and flushes the decay write:

```
constructor(registry, matrixRepo)
```

When `YELLOW → GREEN` decay fires, call `matrixRepo.updateNodeAlert(node.nodeId, 'GREEN')` immediately after mutating ECS.

### Error handling

Repo write failures are non-fatal for gameplay: log the error, do not throw. ECS state is authoritative for the current session; DB is the persistence layer for restarts.

## Track 2: Matrix-Node Mission Targets

### Breach completion model

Completion of a HACK objective is determined by **successful action count**, not alert level. The current `alertLevel === 'RED'` proxy in `MissionSystem` is replaced.

`MissionTargetComponent` gains an optional `hackThreshold?: number`. For HACK objectives, the system checks:

```
node.breachProgress >= target.hackThreshold
```

`breachProgress` is a new field on `MatrixNodeComponent` (default `0`), incremented by each successful brute or sleaze action.

### Data model changes

#### `MatrixNodeComponent`

Add: `breachProgress: number` — count of successful Matrix actions against this node.

#### `MissionTargetComponent`

Add: `hackThreshold?: number` — required for HACK goal type; undefined for KILL/COLLECT/VISIT.

#### `MissionInstanceData`

Add: `nodeTargetData: { roomSlug: string; objectiveIndex: number; hackThreshold: number; }[]`

Defaults to `[]` for non-MATRIX mission types.

### Mission generator

`MissionGenerator` populates `nodeTargetData` for `MATRIX`-type missions:

- Pick a target room from the layout that has (or plausibly has) a Matrix access point.
- Generate a `hackThreshold` of `2 + difficulty` (baseline: 2 successful hacks for easy, scaling with template difficulty).
- Emit a `HACK_NODE` objective with a matching `objectiveIndex`.

### Mission target attachment — lazy at jack-in

Mission acceptance (`acceptMission`) stores `nodeTargetData` in the DB `targetData` JSON blob. No ECS attachment happens at acceptance time because the node entity may not exist yet.

`getOrCreateEcsNode(roomId)` is the attachment point. After creating a new node entity:

1. Query `MissionRepository` for active missions whose `targetData.nodeTargetData` contains an entry matching `roomId`.
2. For each match, attach `MissionTargetComponent` to the node entity:
   - `missionId`, `objectiveIndex`, `goalType: 'HACK'`, `hackThreshold`, `isCompleted: false`.

`MissionService` is injected into `MatrixService` to support this lookup, or the lookup is passed as a callback to keep the dependency direction clean. **Preferred:** callback injection to avoid a circular service dependency.

### `MissionSystem` update

Replace HACK detection logic:

```typescript
} else if (target.goalType === 'HACK') {
  const node = this.registry.getComponent<MatrixNodeComponent>(targetId, ComponentTypes.MatrixNode);
  if (node && target.hackThreshold !== undefined && node.breachProgress >= target.hackThreshold) {
    isMet = true;
  }
}
```

## Track 3: Overwatch Score Stub

### Purpose

Establish the OS accumulator now so Phase 4.3 can add threshold triggers, GOD trace mechanics, and spider adversarial rolls without retrofitting a new field into every Matrix action path.

### Changes

#### `DeckerComponent`

Add: `overwatchScore: number` — initialized to `0` at jack-in.

#### Accumulation

`MatrixService` increments `overwatchScore` by `1` after each dispatched Matrix action (brute, sleaze, data-spike), regardless of success or failure. This matches Shadowrun's model: every action increases GOD attention.

#### Consequences

None in Phase 4.2. The field exists, accumulates, and is visible in debug/admin output. Phase 4.3 will add:
- Alert escalation thresholds driven by OS
- Corporate spider NPC detection rolls (adversarial, probability scales with failures)
- GOD trace and forced jack-out at OS ceiling
