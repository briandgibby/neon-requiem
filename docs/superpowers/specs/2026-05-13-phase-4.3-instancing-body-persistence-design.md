# Phase 4.3 — Mission Instancing, Physical Body Persistence & Alert Escalation

**Date:** 2026-05-13
**Branch:** feat/phase-4.3 (planned)
**Depends on:** Phase 4.2 (complete)

---

## Overview

Two tightly coupled systems delivered together:

1. **Per-party mission instances** — private copies of hostile areas generated at mission acceptance, eliminating shared-world resource contention and admin/clan abuse vectors.
2. **Physical body persistence for deckers** — a decker's body remains anchored in the room where they jacked in, fully vulnerable to physical mob attack, with no legitimate path to relocate it mid-operation.

These are unified through a **shared alert state** that bridges the matrix and physical planes: a matrix breach escalates physical security, and a physical alarm escalates matrix ICE — both players and the environment respond to the same threat level.

---

## Goals

- Mission access requires no OAD keys, no server reset, no spawn camping
- No admin or large-clan abuse vectors
- Decker bodies are fully vulnerable while jacked in — no cheese relocation tactics
- Alert state is a single value shared across both planes per instance
- Memory footprint is proportional to active exploration (lazy ECS spawning)
- Safe zones are a first-class concept with a baked-in event override path

## Non-Goals (Follow-on Phases)

- **Mob aggro / follow system** — room-to-room chase and safe zone boundary enforcement
- **Body-guarding mechanic** — tank actively shields a jacked-in decker's physical body
- **Oracle/overwatch NPC archetype** — flavor NPCs for specific missions
- **Admin tooling** for live instance monitoring

## Instance Lifecycle

A `MissionInstance` record is created at `acceptMission` time alongside the existing `MissionInstanceData` generation. Its lifecycle:

```
PENDING → ACTIVE → COMPLETED | ABANDONED
```

- **PENDING**: created at acceptance; rooms exist in DB but nothing is in ECS memory
- **ACTIVE**: first party member physically enters any instance room
- **COMPLETED**: mission objectives resolved
- **ABANDONED**: all party members have been absent from the instance for a configurable timeout (default 10 minutes)

On resolution, all ECS entities tied to the instance are evicted from memory and instance DB records are soft-deleted (or archived for audit). Players are returned to their last known world room.

---

## Room Architecture

At acceptance, `InstanceRoom` records are created for each room in the generated layout. These are distinct from world rooms — they share a `templateRoomSlug` for reference but carry unique IDs so there is no ID collision with persistent world rooms.

**`InstanceRoom` fields:**
| Field | Type | Notes |
|-------|------|-------|
| `id` | String (uuid) | Unique per instance |
| `instanceId` | String | FK → `MissionInstance` |
| `templateRoomSlug` | String | The world template this room is based on |
| `alertLevel` | Enum GREEN/YELLOW/RED | Per-room, driven by instance alertLevel |
| `clearedAt` | DateTime? | Set when all mobs in this room are eliminated |
| `isSafeZone` | Boolean | Always `false` for instance rooms |

If the mission has a MATRIX objective, an instance-scoped `MatrixNode` is also created at acceptance, with `linkedRoomId` pointing to the correct `InstanceRoom` and `requiresPhysicalPresence: true`.

## ECS Memory Model (Lazy Spawning)

Nothing in an instance exists in ECS memory until a player enters a room. On first entry:

1. Read the room's mob template list from DB
2. Spawn ECS entities for all mobs assigned to that room
3. For matrix nodes: create the ECS node entity only when the first player jacks in

This keeps server memory proportional to explored area. Mob entities for rooms no player has entered do not exist. ICE entities follow the existing lazy spawning behavior already in `getOrCreateEcsNode`, extended to instance nodes.

**Room cleared:** when all mob entities in an instance room are dead, the room is flagged `clearedAt`. Cleared rooms do not re-spawn mobs (permanent clear for the life of the instance).

**Alert-driven re-spawn:** at RED alert, elite mob entities can spawn into any un-cleared room regardless of whether it was previously empty. This is the one exception to the "cleared = permanent" rule — elite reinforcement ignores the cleared flag.

## Physical Body Persistence (Option A)

A single ECS entity per player. `DeckerComponent` gains one new field: `physicalRoomId: string`.

### Field Lifecycle

| Event | `PositionComponent.roomId` | `DeckerComponent.physicalRoomId` |
|-------|--------------------------|----------------------------------|
| Normal movement | Tracks current world/instance room | Not present |
| `jackIn` issued | Set to matrix node's linked room | Set to the room where `jackIn` was issued |
| Matrix navigation | Updates to current node's room | Unchanged (body stays put) |
| `jackOut` | Restored to `physicalRoomId` | Cleared |
| Emergency jack-out | Restored to `physicalRoomId` | Cleared |

### Body Anchoring (Anti-Cheese)

Once `DeckerComponent` is present on an entity:

- All movement commands on that entity return: *"Your body is unresponsive — you are deep in the matrix."*
- The follow mechanic cannot target a jacked-in entity as the leader
- No drag, carry, or forced-move interactions can change a jacked-in entity's `PositionComponent`
- `physicalRoomId` is treated as immutable for the session — it is set once at `jackIn` and only cleared at `jackOut`

This eliminates the exploit of jacking in from a hostile room then relocating the body to an unpatrolled area.

### Body Vulnerability

Mob AI reads `physicalRoomId` (not `PositionComponent.roomId`) when selecting targets for a jacked-in entity. Before attacking, mob AI checks the effective safe zone status of the `physicalRoomId` room:

```
effectiveSafeZone = room.isSafeZone && !room.safeZoneOverrideActive
```

If the body's room is not a safe zone (all instance rooms), the decker is a valid attack target. If body HP reaches 0 while jacked in, an emergency jack-out is triggered automatically, applying dumpshock damage through the existing `jackOut(isEmergency: true)` path.

### Physical Presence Requirement for Instance Nodes

`MatrixNode` gains `requiresPhysicalPresence: Boolean @default(false)`. Instance nodes have this set to `true`.

`jackIn` validates: if the target node has `requiresPhysicalPresence: true`, the player's current room must belong to the same `MissionInstance` as the node's `linkedRoomId`. Attempting to jack in remotely returns: *"This host requires a hardline connection — you need to be on-site."*

Player-character remote hacking of instance nodes is explicitly not supported. The Oracle/overwatch archetype is reserved for NPC flavor roles in specific mission designs.

## Shared Alert State

`MissionInstance` holds the authoritative `alertLevel` for the entire instance (both planes).

### Escalation Paths

**Matrix → Physical:**
When the matrix node's `alertLevel` changes (via `MatrixTickSystem` or player actions), the `MissionInstance.alertLevel` is updated to the higher of the two values. Physical mob AI and patrol frequency read `MissionInstance.alertLevel`.

**Physical → Matrix:**
When `CombatService` or a future `SecurityPatrolSystem` triggers a physical alarm (combat detected in a secure area, guard body found), `MissionInstance.alertLevel` escalates. The matrix node's `alertLevel` is updated to match on the next tick.

Alert levels only escalate within a session — there is no automatic decay back to GREEN during an active mission. Decay is reserved for specific gameplay actions (e.g., successfully using `sleaze` to suppress an alert).

### Per-Level Behavior

| Alert | Physical Instance | Matrix Node |
|-------|------------------|-------------|
| **GREEN** | Guards in fixed positions; utility/secondary rooms unpatrolled; no elite mobs | ICE is reactive — only responds when attacked |
| **YELLOW** | Guards begin active sweeps; patrol routes expand to adjacent rooms; decker's physical room will receive patrol traffic within ticks | ICE becomes proactive — initiates attacks without waiting |
| **RED** | All rooms including utility spaces patrolled; elite mobs spawn into un-cleared rooms; assault frequency at maximum | ICE reinforced with additional entity spawns; BLACK ICE may appear |

---

## Elite Mobs

Elite mobs are corporation-specific archetypes defined in the `MobTemplate` table with `eliteOnly: true` and a `corporationId` FK. They never spawn at GREEN or YELLOW. At RED alert, the instance spawning system checks whether any elite templates are registered for the corporation that owns this instance's target facility, and spawns them into active (player-occupied) rooms.

Examples by corporation:
- Renraku → Red Samurai
- Aztechnology → Jaguar Guard
- Ares → Knight Errant SWAT
- Saeder-Krupp → Dragon-Forged Security (future)

Elite mob stats and any special abilities are defined entirely in the template — no hardcoded special-casing in the spawning logic.

## Safe Zones

### World Rooms
| Field | Default | Meaning |
|-------|---------|---------|
| `isSafeZone` | `false` | Must be explicitly set for public/social areas |
| `safeZoneOverrideActive` | `false` | Temporarily disables safe zone protections |

`effectiveSafeZone = isSafeZone && !safeZoneOverrideActive`

Mob AI, matrix ICE targeting, and PvP checks all use `effectiveSafeZone`. Setting `safeZoneOverrideActive = true` via `WorldEventService` is sufficient to allow invasion-event mobs into previously protected areas — no entity logic changes required.

### Instance Rooms
`isSafeZone` is always `false`. Instance rooms offer no safe zone protection regardless of event state.

## Data Model Changes

### New Tables
```prisma
model MissionInstance {
  id               String   @id @default(uuid())
  missionId        String
  status           InstanceStatus @default(PENDING)
  alertLevel       AlertLevel @default(GREEN)
  partyCharacterIds String[] // denormalized for fast lookup
  createdAt        DateTime @default(now())
  activatedAt      DateTime?
  resolvedAt       DateTime?
  rooms            InstanceRoom[]
}

model InstanceRoom {
  id               String   @id @default(uuid())
  instanceId       String
  instance         MissionInstance @relation(fields: [instanceId], references: [id])
  templateRoomSlug String
  alertLevel       AlertLevel @default(GREEN)
  clearedAt        DateTime?
  isSafeZone       Boolean  @default(false)
}

enum InstanceStatus {
  PENDING
  ACTIVE
  COMPLETED
  ABANDONED
}
```

### Modified Tables
```prisma
// Room (world rooms)
isSafeZone            Boolean @default(false)
safeZoneOverrideActive Boolean @default(false)

// MatrixNode
requiresPhysicalPresence Boolean @default(false)

// MobTemplate
eliteOnly     Boolean @default(false)
corporationId String?
```

## Architecture Touch Points

| Layer | What Changes |
|-------|-------------|
| `MissionService.acceptMission` | Create `MissionInstance` + `InstanceRoom` records; create instance-scoped `MatrixNode` if applicable |
| `MatrixService.jackIn` | Set `physicalRoomId` on `DeckerComponent`; validate `requiresPhysicalPresence` |
| `MatrixService.jackOut` | Restore `PositionComponent.roomId` from `physicalRoomId`; clear field |
| `CommandDispatcher` (movement) | Block movement if entity has `DeckerComponent` |
| `MatrixTickSystem` | Write alert escalation to `MissionInstance.alertLevel` |
| `MobAiSystem` / `SecurityPatrolSystem` | Read `physicalRoomId` for jacked-in targets; check `effectiveSafeZone` |
| Instance spawning (new) | Lazy-spawn mob ECS entities on room entry; elite spawn on RED alert |
| `WorldEventService` (new/extend) | Set `safeZoneOverrideActive` on rooms during event windows |
| `InstanceCleanupSystem` (new) | Evict instance ECS entities on COMPLETED/ABANDONED; soft-delete DB records |
